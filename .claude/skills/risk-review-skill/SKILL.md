# risk-review-skill

募集部（coconala-jobmatching）のADR「募集部におけるリスク判定・開発承認およびリリースフローの定義」に基づき、PR/Issueのリスクレベル（A/B/C/D）を判定するスキル。

## 役割と前提

このスキルの出力は **PO/GM にレビュー依頼を出すための叩き台** である。最終的なリスク認識・承認判断は PO/GM が行うため、Claude 側で過度に断定したり、逆に過度にヘッジして結論を曖昧にする必要はない。

- **目的**: 承認者（PO/GM/テックリード）が短時間で判断できる材料を提示すること
- **読者**: 承認者（忙しい）と記入者（自分でセルフチェックする人）
- **依存ツール**: `gh`（GitHub CLI、認証済み）
- **想定ドメイン**: 募集部単独の変更。スキルマーケット（本体側）に影響する変更の場合は、本体側のリスク判定基準に従う旨を出力に明示する

## ワークフロー

### Step 1: 対象のPR/Issueを確認

ユーザーが対象を明示していない場合は、まず以下を尋ねる:

> どのPR/Issueのリスク判定をしますか？以下のいずれかを教えてください:
> - PRまたはIssueのURL（例: `https://github.com/welself/coconala-jobmatching/pull/1234`）
> - 番号のみ（その場合はリポジトリも教えてください）

URLからは `owner`, `repo`, タイプ（pr/issues）, 番号をパースする。番号のみの場合は `owner/repo` を別途確認する。

### Step 2: 内容の取得

`gh` CLI で対象の情報を取得する。PRの場合は差分情報も取得する。

**PRの場合:**
```bash
gh pr view <number> --repo <owner>/<repo> --json title,body,author,labels,files,additions,deletions,changedFiles
gh pr diff <number> --repo <owner>/<repo>
```

**Issueの場合:**
```bash
gh issue view <number> --repo <owner>/<repo> --json title,body,author,labels,comments
```

Issueの場合、本文だけでなく**コメント欄に対応方針・影響範囲・検証結果がまとめられていることが多い**ので、コメントも必ず確認する。

差分が大きすぎてコンテキストを圧迫しそうな場合は、まず変更ファイル一覧（`--files`）と概要だけを取得し、必要に応じて個別ファイルの差分を確認する。

### Step 3: リスクレベルの判定

下記「判定基準」セクションのテーブルに基づいて、A/B/C/Dを判定する。

判定の進め方:
1. まずレベルAの判定基準のいずれかに該当するか確認（該当すれば即A）
2. 該当しなければレベルBの判定基準を確認
3. 以下、C→Dの順で確認
4. C/Dの境界が曖昧な場合は「C/D境界の判定目安」を参照

**重要な観察ポイント:**
- 変更ファイルのパス（認証関連、メッセージ機能、応募/選考フロー、企業管理画面など主要導線か）
- 追加/削除行数（大規模な変更か）
- DBマイグレーション・スキーマ変更の有無
- API contract / GraphQL schema の変更
- フィーチャーフラグの利用有無
- メンテナンスを伴うか、伴う場合の時間

判定の最終判断は PO/GM に委ねるため、Claude は **「自分の判定の決め手」と「逆方向のリスク（上下のレベルの可能性）」を明示** すれば十分。ヘッジのし過ぎ（「Aの可能性もあるし、Bの可能性もあるし、Cかもしれない」）は読み手に判断材料を渡せないので避ける。

### Step 4: 結果の出力

下記「出力フォーマット」に従って結果を提示する。

### Step 5: コメント投稿の確認

結果を出した後、必ず以下を尋ねる:

> この判定結果をPR/Issueにコメントとして投稿しますか？
> 1. はい、そのまま投稿
> 2. はい、ただし投稿前に内容を編集したい
> 3. いいえ、出力のみで十分

- 「はい、そのまま投稿」の場合: `gh pr comment <number> --repo <owner>/<repo> --body-file <tmpfile>` または `gh issue comment` で投稿
- 「編集したい」の場合: ユーザーの修正指示を受けてから投稿
- 「いいえ」の場合: 何もしない

投稿後は、投稿先のURLを出力する。

## 出力フォーマット

判定結果は以下のフォーマットで出力する（Markdown形式）。コメントとして投稿する際もそのまま使える内容にする。

```markdown
## リスクレベル判定結果

**判定: レベル[A/B/C/D]**

### 判定根拠

- 変更内容: [一行サマリ]
- 該当基準: [マッチしたADRの判定基準（複数なら主要なもの）]
- [判定の決め手となった事実を 1〜3 個。検証結果、影響範囲、データ処理/認証/API contractの有無など]

### 必要な対応

| 項目 | 要否 | 備考 |
| :--- | :--- | :--- |
| 開発承認者 | [部長+GM / GM or 部長 / TL or GM / 不要] | [あれば一言] |
| リリース手順（リバート含む）の事前記載 | [必須 / 推奨 / 不要] | [あれば一言] |
| #released チャンネル投稿 | [必須 / 推奨 / 不要] | [あれば一言] |

### 補足

- [なぜ一段上/下のレベルではないか、保守的に上げた/下げた判断、レビュー時に承認者が知っておくと有用な追加情報など]

### レビュー依頼前の確認事項（記入者向け）

- [ ] [PO/GM に依頼を出す前に、記入者自身がチェック・準備すべきこと]
- [ ] [例: 影響範囲が確かに募集部に閉じているか再確認]
- [ ] [例: △△のテスト結果を本Issue/PRに添付済みか]

---
*本判定は[募集部ADR](https://github.com/welself/coconala-jobmatching/discussions/534)に基づきます。最終判断は承認者にてお願いします。*
```

### フォーマット運用ルール

承認者が一読で判断できることを最優先する。以下の運用に従う:

1. **判定根拠は 3〜5 項目で凝縮する**。冗長な前置きや当たり前のことは書かない。「該当基準」「決め手の事実」「検証結果」「逆方向に振れる/振れない理由」だけで十分。
2. **補足は「ある時だけ」出す**。書くことがなければセクションごと省略する。典型的に書くべき内容は:
   - なぜ一段上のレベルにしなかったか / 一段下にしなかったか
   - 保守的に Cで提示しているが単独なら D 相当 のような注釈
   - 承認者が知っておくと判断が楽になる文脈
3. **「レビュー依頼前の確認事項」は記入者（=依頼を出す本人）向けの TODO**である。承認者向けの注意書きではない。書く内容は記入者自身が PO/GM に依頼を出す前に手を動かして確認・準備すべきことに限る。例:
   - [ ] テスト結果のスクショ/ログを本Issueに添付したか
   - [ ] 影響範囲が募集部に閉じているか再確認したか（本体側DBに触れていないか）
   - [ ] 関係者（Biz/CS等）への事前共有が必要かを確認したか
   - 確認事項がなければセクションごと省略する
4. **Claude 自身の不確実性は「補足」または「判定根拠」に溶かす**。「不確実性・確認事項」のような Claude のヘッジ専用のセクションは作らない。判定を曖昧にすると承認者の判断コストが上がる。
5. **重要な数字や事実は太字や箇条書きで強調**。長い散文で埋もれさせない。

## 判定基準（ADRより）

### レベルA: 経営/ユーザーに大きな打撃を与えるもの

| 判定基準 | 具体例 |
| :--- | :--- |
| 個人情報・企業機密情報の漏えいにつながるもの | 応募者の個人情報、企業の選考基準・評価情報 |
| 機密データ扱いに関わるロジック変更 | メッセージ/トークルームのロジック変更 |
| セキュリティに関わるもの | 認証・認可の変更 |
| 流通高への大幅な影響 | 成約数に直結する基盤ロジックの変更 |
| 大規模のシステム利用停止 | |
| 復旧不可能なデータ消失 | |
| メンテナンスを伴うリリース（3時間超） | |

- **開発承認者**: 募集部部長 ＋ 募集部GM
- **リリース手順（リバート含む）**: 必須
- **releasedチャンネル投稿**: 必須

### レベルB: 主要機能・流通高への影響

| 判定基準 | 具体例 |
| :--- | :--- |
| 流通高への影響 | 応募数・成約数に影響する変更 |
| メンテナンスを伴うリリース（3時間以下） | |
| 主要導線のデータ処理ロジック変更（応募フロー） | 応募情報の登録・変更・バリデーション処理 |
| 主要導線のデータ処理ロジック変更（選考フロー） | 選考ステータスの変更処理 |
| 主要導線のデータ処理ロジック変更（メッセージ機能） | メッセージ送受信のロジック |
| 主要導線のデータ処理ロジック変更（企業管理画面） | 請求・契約管理の処理 |
| 意図的に出力しているログの欠損 | |
| メール・プッシュ通知でユーザー影響が大きいもの | |

- **開発承認者**: 募集部GM または 募集部部長
- **リリース手順（リバート含む）**: 必須
- **releasedチャンネル投稿**: 必須

### レベルC: 全体に影響するが、Bほどではないもの

| 判定基準 | 具体例 |
| :--- | :--- |
| 周辺機能の変更（データ処理を含む） | |
| 軽微なデータ不整合の可能性 | |
| 主要導線の文言・UI修正（データ処理を伴わないもの） | エラーメッセージ修正、ボタンラベル変更 |
| 意図しないログ出力の変更 | |

- **開発承認者**: テックリード または 募集部GM
- **リリース手順（リバート含む）**: 推奨（エンジニア判断）
- **releasedチャンネル投稿**: 推奨

### レベルD: 限定的な範囲への影響

| 判定基準 | 具体例 |
| :--- | :--- |
| リファクタリング（既存動作に影響なし） | |
| テスト追加 | |
| ドキュメント・コメント修正 | |
| スタイル調整（CSS等） | |
| 技術的負債の解消（影響範囲が限定的） | |

- **開発承認者**: 不要（GitHubレビューのみ）
- **リリース手順**: 不要
- **releasedチャンネル投稿**: 不要

### B/Cの境界

「応募画面の改修」でも:
- バリデーション・データ登録処理の変更 → **B**
- 文言・UI修正のみ → **C**

### C/D境界の判定目安

**レベルCを検討する観点**（最終判断は実装者・レビュアーに委ねる）:
- 複数画面 / 複数フローに影響する
- 共通コンポーネント（layout / header / auth wrapper 等）に触る
- API contract / GraphQL schema / resolver の挙動変更がある
- 監視・ログ・エラーハンドリング（通知含む）の変更がある
- 軽微でもデータ不整合の可能性がある
- Biz / CS / Ops との連携（告知やサポート準備など）が必要

**レベルDの典型例**:
- 影響が局所的（単一コンポーネント / 単一ファイル / 単一ページ程度）
- 主要導線の挙動変更なし
- API / schema の変更なし
- データ書き込み・移行・バリデーション変更なし
- 即時リバートで復旧できる

運用意図: Cは「報告なしでリリースするには少し不安」なもの、Dは「報告・承認なしで実装者の判断でリリースしてよい」もの。

### クロスドメイン変更の扱い

スキルマーケット（本体側）の機能・データ・売上に影響を与える可能性がある変更の場合、本ADRではなく**本体側のリスクレベル判定基準**に従う必要がある。

判定中に本体側への影響が疑われる場合（例: 本体側コードへの変更、共通ライブラリの変更、共通DBテーブルの変更など）、ユーザーにその旨を明示し、本体側基準への切替を促す。

## 例

### 例1: 文言修正のみのPR

入力: 応募完了画面のボタンラベルを「送信」→「応募する」に変更するPR、変更ファイル1つ、+1/-1行。

出力例:
```markdown
## リスクレベル判定結果

**判定: レベルC**

### 判定根拠

- 変更内容: 応募完了画面のボタンラベル変更（「送信」→「応募する」）
- 該当基準: 「主要導線の文言・UI修正（データ処理を伴わないもの）」
- 影響範囲は単一画面の1行のみ、データ処理ロジック・API contractの変更なし

### 必要な対応

| 項目 | 要否 | 備考 |
| :--- | :--- | :--- |
| 開発承認者 | テックリード または 募集部GM | |
| リリース手順（リバート含む）の事前記載 | 推奨 | revert PR 一発で戻せる旨を明記しておくと安全 |
| #released チャンネル投稿 | 推奨 | 主要導線の文言変更のため、Biz/CSにも共有しておくと親切 |

### 補足

- 単独なら D 相当だが、主要導線（応募フロー）の文言のため保守的に C で提示
```

### 例2: テスト追加のみのPR

入力: 既存ロジックのユニットテストを追加するPR、テストファイルのみの変更。

出力例:
```markdown
## リスクレベル判定結果

**判定: レベルD**

### 判定根拠

- 変更内容: 既存ロジックのユニットテスト追加
- 該当基準: 「テスト追加」
- プロダクションコードに変更なし、即時リバート可能

### 必要な対応

| 項目 | 要否 | 備考 |
| :--- | :--- | :--- |
| 開発承認者 | 不要（GitHubレビューのみ） | |
| リリース手順（リバート含む）の事前記載 | 不要 | |
| #released チャンネル投稿 | 不要 | |
```

### 例3: 認証ロジックの変更

入力: ログイン処理にOAuthプロバイダを追加するPR。

出力例:
```markdown
## リスクレベル判定結果

**判定: レベルA**

### 判定根拠

- 変更内容: ログイン処理へのOAuthプロバイダ追加
- 該当基準: 「セキュリティに関わるもの（認証・認可の変更）」
- 認証フローの根本的な変更を伴う

### 必要な対応

| 項目 | 要否 | 備考 |
| :--- | :--- | :--- |
| 開発承認者 | 募集部部長 ＋ 募集部GM | |
| リリース手順（リバート含む）の事前記載 | 必須 | |
| #released チャンネル投稿 | 必須 | |

### 補足

- ログイン機能が共通基盤側（本体スキルマーケット）にも影響する場合、本体側のリスク判定基準を適用する必要あり

### レビュー依頼前の確認事項（記入者向け）

- [ ] 本体側（スキルマーケット）の認証基盤に影響しないか確認したか
- [ ] ステージング環境での認証フロー確認のスクショ/ログを添付したか
```

## コメント投稿時のコマンド例

PR の場合:
```bash
gh pr comment <number> --repo <owner>/<repo> --body-file <tmpfile>
```

Issue の場合:
```bash
gh issue comment <number> --repo <owner>/<repo> --body-file <tmpfile>
```

長文・改行を含むコメントは `--body` 引数より `--body-file` でファイル経由の方が安定する。一時ファイルは `mktemp` で作成し、投稿後に削除する。

## 注意事項

- 判定はあくまで支援であり、最終的なリスク認識・承認判断は承認者（PO/GM/テックリード）が行う。出力の末尾にその旨を必ず含める。
- ADRには「あえて曖昧にしている部分」がある（流通高の定量基準、B/Cの具体例など）。Claude 側で過度に断定はしないが、ヘッジで結論を曖昧にもしない。判定の決め手と一段上下に振れる/振れない理由を補足に書くことで承認者の判断材料を増やす。
- PRに既にリスクレベルの記載がある場合は、それを尊重しつつ、判定結果と乖離があれば理由を添えて指摘する。
