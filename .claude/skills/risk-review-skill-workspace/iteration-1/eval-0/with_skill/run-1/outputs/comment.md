## リスクレベル判定結果

**判定: レベルC**

### 判定根拠

- 変更内容: SentryにキャプチャされているgRPCエラーオブジェクト（`grpcCode`/`message`/`method`/`request`キーを持つ非ErrorインスタンスのオブジェクトがSentryに送られる問題）の改善。対応方針候補は (1) `beforeSend` フックでErrorインスタンスに変換、(2) gRPCクライアントのラッパーで統一、(3) 発生源の調査。
- 該当基準: 「監視・ログ・エラーハンドリング（通知含む）の変更」（C/D境界の判定目安）
- 影響範囲は `jobmatching-web` のSentry連携層に限定。応募/選考/メッセージ等の主要導線のデータ処理ロジック・API contract・認証/認可・DBスキーマには触れない。
- ただし `beforeSend` フックで対応する場合、フィルタロジックの誤りで**意図的に出力しているエラーが欠損する可能性**があるため、保守的にDではなくCで提示。

### 必要な対応

| 項目 | 要否 | 備考 |
| :--- | :--- | :--- |
| 開発承認者 | テックリード または 募集部GM | |
| リリース手順（リバート含む）の事前記載 | 推奨 | `beforeSend` フックの変更はrevert PR一発で戻せる旨を明記推奨 |
| #released チャンネル投稿 | 推奨 | Sentry運用に関わるため、観測側の挙動変更として共有しておくと安全 |

### 補足

- 対応方針が「発生源の調査」のみで終わるならD相当だが、`beforeSend` フックやクライアントラッパーで実装する想定が含まれるため、エラーハンドリング層の挙動変更とみなしてCで提示。
- 採用する実装方針によってリスクが変動する点に留意:
  - **発生源調査のみ / 単純な型変換 → D寄り**
  - **`beforeSend` で広く変換・フィルタする実装 → Cのまま**
  - **意図的に出力していたエラーが結果的に欠損するロジックを含む → B（「意図的に出力しているログの欠損」に該当）に上振れる可能性あり**
